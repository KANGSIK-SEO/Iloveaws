## 2. 인프라 구성 요소 명세표

| 계층 | 리소스명 | 세부 속성 및 설정값 | 설계 의도 및 역할 |
|---|---|---|---|
| **네트워크** | `mission-vpc` | CIDR: `10.0.0.0/16` | 타 사용자와 완전히 격리된 독립 가상 프라이빗 네트워크 공간 |
| **서브넷** | `mission-public-subnet` | CIDR: `10.0.1.0/24`<br>AZ: `ap-northeast-2a` | 외부 인터넷과 통신 가능한 공용 서브넷. 자동 공인 IP 할당 활성화 |
| **게이트웨이** | `mission-igw` | VPC 바인딩 완료 | 사설 VPC와 외부 공용 인터넷 사이의 양방향 패킷 관문 |
| **라우팅** | `mission-public-rt` | `0.0.0.0/0 &rarr; mission-igw`<br>`10.0.0.0/16 &rarr; local` | 서브넷 내부 인스턴스가 인터넷과 통신할 수 있도록 기본 게이트웨이 제공 |
| **컴퓨팅** | `mission-web-server` | Instance: `t3.micro`<br>AMI: Ubuntu 22.04 LTS | AWS 프리티어 대상 가상 서버로 Nginx 웹 서버 호스팅 |
| **스토리지** | EBS Root Volume | Size: `10 GiB gp3`<br>`DeleteOnTermination: true` | 불필요한 스토리지 증설 없이 10GiB로 제한하여 과금 방지 |
| **보안 그룹** | `mission-web-sg` | Inbound: `80 (0.0.0.0/0)`, `22 (내 IP)`<br>Outbound: `ALL` | 불필요한 포트를 원천 차단하고 관리용 SSH는 특정 IP로만 한정 |
| **권한 (IAM)** | `mission-deployer-role` | EC2/VPC 최소 구성 권한만 부여<br>`AdministratorAccess` 금지 | 최소 권한 원칙(Least Privilege)에 따라 권한 범위 제한 |

## 3. 트래픽 흐름 (Traffic Flow Analysis)

### 1) 외부 사용자 &rarr; 웹 서비스 인바운드 흐름 (HTTP:80)
1. 외부 사용자가 브라우저 주소창에 `http://3.34.126.62`를 입력합니다.
2. 패킷이 인터넷을 거쳐 AWS 서울 리전의 **Internet Gateway (`mission-igw`)**에 도달합니다.
3. VPC 내부의 **Route Table (`mission-public-rt`)** 및 대상 Public Subnet(`10.0.1.0/24`)으로 인입됩니다.
4. EC2 가상 방화벽인 **Security Group (`mission-web-sg`)**이 인바운드 규칙(`0.0.0.0/0 &rarr; tcp:80`)을 검사하여 패킷을 통과시킵니다.
5. Ubuntu OS 내부의 Nginx 프로세스(`0.0.0.0:80`)가 요청을 수신하여 `index.html` 또는 `/health` 고정 응답을 생성합니다.

### 2) 웹 서버 &rarr; 외부 사용자 아웃바운드 응답 흐름
1. Nginx가 생성한 HTTP 200 OK 응답 패킷이 인스턴스 네트워크 인터페이스(ENI)를 떠납니다.
2. Security Group은 **상태 저장형(Stateful)** 방화벽이므로, 허용된 인바운드 요청에 대한 응답은 아웃바운드 규칙과 무관하게 자동 허용됩니다.
3. 서브넷 라우트 테이블의 `0.0.0.0/0 &rarr; mission-igw` 규칙에 따라 패킷이 Internet Gateway로 전달됩니다.
4. Internet Gateway가 인스턴스의 사설 IP(`10.0.1.15`)를 공인 IP(`3.34.126.62`)로 1:1 NAT 변환하여 최종 사용자 브라우저에 전달합니다.

### 3) 인스턴스 자체의 아웃바운드 인터넷 통신 (패키지 설치 및 외부 API)
- 인스턴스 내부에서 `curl https://example.com` 또는 `apt-get update` 실행 시, 라우팅 테이블과 IGW를 통해 인터넷 외부 호스트와 성공적으로 통신합니다.
